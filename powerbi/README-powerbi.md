# Power BI 用电分析报表 · 建模说明

在 `smart_home` 数据库之上搭建的三页用电分析报表。数据库层负责采集与预聚合，
Power BI 层负责多维分析与呈现，两层职责分离。

搭建步骤见 [`操作指引.md`](操作指引.md)。

---

## 一、数据模型

星型模型，2 张事实表 + 2 张维度表。

```
                  dim_date
                 （DAX 新建）
                  Date / 年 / 月
                  / 星期 / 是否周末
                        │
            ┌───────────┴───────────┐
            │ 1                     │ 1
            ▼ *                     ▼ *
      fact_power                fact_alert
   power_usage / 时间戳     报警类型 / 处理状态
            ▲ *                   ▲ *
            │ 1                   │ 1
            └───────────┬───────────┘
                        │
                   dim_device
              设备编号 / 设备名称
              / 设备类型 / 额定功率
```

| 表 | 来源 | 行数 | 粒度 |
| --- | --- | --- | --- |
| `fact_power` | `power_consumption` | 51,480 | 设备 × 15 分钟 |
| `fact_alert` | `alerts` | 600 | 单条报警 |
| `dim_device` | `devices` | 7 | 单台设备 |
| `dim_date` | DAX `CALENDAR` | 92 | 单日 |

连接方式为 **导入模式**。数据量在 5 万行量级，DirectQuery 只会白白牺牲时间智能函数
和查询性能，没有收益。

### 为什么库里有四张统计表，却不在报表里用

`hourly_stats` / `daily_stats` / `weekly_stats` / `monthly_stats` 四张统计表
是**数据库侧的预聚合层**，服务于本项目的 Node-RED 实时看板 —— 那里要求单点控制
响应 ≤ 0.5 秒、批量 ≤ 1 秒，每次查询都扫 5 万行明细无法达标，所以用统计表把
聚合结果物化下来。

Power BI 是**分析侧**，需求不同：需要按任意维度组合下钻（设备 × 类型 × 时段 × 星期 ×
是否周末），而预聚合表按固定粒度物化后就丢失了这种灵活性。因此报表直接基于
`power_consumption` 明细重建模，把聚合交给 DAX 引擎。

两层不是重复劳动，是各自服务不同的查询模式：

| | 数据库统计表 | Power BI 模型 |
| --- | --- | --- |
| 服务对象 | Node-RED 实时看板 | 分析报表 |
| 响应要求 | ≤ 0.5 秒 | 秒级可接受 |
| 聚合粒度 | 预设四种 | 任意维度组合 |
| 存储成本 | 物化，占空间 | 内存中按需计算 |

## 二、数据可信度

模拟数据容易沦为随机数，这张表的用电量是按物理模型生成的，可以反算校验。

**生成公式**

```
单条用电量(度) = 额定功率(kW) × 0.25 小时
                 × 负载率 × 设备系数 × 周末系数 × 随机抖动
```

乘积统一经 `LEAST(..., 1.00)` 截断，**保证任意一条记录都不超过该设备在 15 分钟内的
理论最大用电量**（额定功率 × 0.25 小时）。即电器始终运行在额定功率以内。

**实测校验**（7 台设备全部通过）

| 设备 | 额定功率 | 15 分钟理论上限 | 实际峰值 | 校验 |
| --- | --- | --- | --- | --- |
| 客厅空调 | 1500 W | 0.3750 度 | 0.3750 | OK |
| 卧室空调 | 1200 W | 0.3000 度 | 0.2428 | OK |
| 客厅风扇 | 75 W | 0.0188 度 | 0.0188 | OK |
| 客厅主灯 | 60 W | 0.0150 度 | 0.0150 | OK |
| 卧室风扇 | 60 W | 0.0150 度 | 0.0129 | OK |
| 卧室灯 | 40 W | 0.0100 度 | 0.0097 | OK |
| 厨房灯 | 30 W | 0.0075 度 | 0.0065 | OK |

校验语句：

```sql
SELECT d.device_name,
       ROUND(d.power_rating / 1000 * 0.25, 4) AS 理论上限,
       MAX(p.power_usage)                     AS 实际峰值
FROM power_consumption p
JOIN devices d ON d.device_id = p.device_id
GROUP BY d.device_name, d.power_rating;
```

> 表中数值取自一次代表性运行。由于生成过程含 `RAND()` 抖动，
> **每次重建会有 ±1% 左右的浮动**，但各表行数恒定，且「实际峰值 ≤ 理论上限」
> 这一约束在任意一次运行中都成立 —— 校验语句应始终返回 0 行超限记录：
>
> ```sql
> SELECT COUNT(*) AS 超限记录数
> FROM power_consumption p
> JOIN devices d ON d.device_id = p.device_id
> WHERE p.power_usage > ROUND(d.power_rating / 1000 * 0.25, 4);
> ```

**负载率模型**（0 ~ 1，1.0 = 满负荷运行）

| 设备类型 | 时段 | 负载率 |
| --- | --- | --- |
| 空调 | 18:00–22:00 晚间制冷高峰 | 0.80 |
| 空调 | 12:00–13:00 午间 | 0.70 |
| 空调 | 01:00–05:00 夜间睡眠模式 | 0.20 |
| 空调 | 其余时段 | 0.40 |
| 照明 | 18:00–23:00 晚间 | 0.85 |
| 照明 | 06:00–07:00 早起 | 0.50 |
| 照明 | 01:00–05:00 | 0.00（不产生记录） |
| 照明 | 其余时段 | 0.12 |
| 风扇 | 11:00–15:00 午后 | 0.80 |
| 风扇 | 18:00–21:00 | 0.45 |
| 风扇 | 01:00–05:00 | 0.00（不产生记录） |
| 风扇 | 其余时段 | 0.18 |

负载率为 0 时不写入记录，因此 `record_count` / `记录条数` 有实际业务含义
（代表设备处于开机状态的采样次数），而不是恒等于采样点总数。

**生成结果**

| 指标 | 值 | 是否随重建变化 |
| --- | --- | --- |
| 数据区间 | 2026-07-02 ~ 2026-09-29（90 天） | 否 |
| 明细行数 | 51,480 | 否 |
| 总用电量 | 约 2,721 度 | ±1% |
| 日均用电 | 约 30.2 度 | ±1% |
| 周末日均 / 工作日日均 | 约 32.3 / 29.4 度 | ±1% |
| 凌晨 01:00–05:00 照明与风扇记录数 | 0 | 否 |

行数恒定是因为每条记录对应一个确定的时间槽 × 设备组合，与随机抖动无关；
只有电量数值受 `RAND()` 影响。

## 三、DAX 度量值清单

全部建在 `_Measures` 空表中（**建模 → 新建表** → `_Measures = { BLANK() }`），
避免度量值散落在事实表里。

### 基础量值

```dax
总用电量 = SUM(fact_power[power_usage])
```
格式：`0.00 "度"`

```dax
记录条数 = COUNTROWS(fact_power)
```
格式：`#,0`

```dax
峰值功率 = MAX(fact_power[power_usage])
```
格式：`0.0000 "度/15分钟"`

```dax
日均用电 = DIVIDE([总用电量], DISTINCTCOUNT(fact_power[日期]))
```
格式：`0.00 "度"`

```dax
设备数 = DISTINCTCOUNT(dim_device[设备编号])
```
格式：`#,0`

### 使用强度

依赖 `fact_power[负载率]` 计算列（见 `操作指引.md` 第 5.1 节）。

```dax
平均负载率 = AVERAGE(fact_power[负载率])
```
格式：`0.0%`

```dax
高负载时段占比 =
DIVIDE(
    CALCULATE([记录条数], fact_power[负载率] >= 0.85),
    [记录条数]
)
```
格式：`0.0%`。衡量设备有多少比例的运行时间处于接近满负荷的状态。

```dax
单设备日均用电 = DIVIDE([总用电量], [设备数] * DISTINCTCOUNT(fact_power[日期]))
```
格式：`0.00 "度"`
用以横向比较不同设备，消除设备台数和天数的影响。

### 时间对比

只做**环比**，不做同比 —— 数据只有 90 天，同比会全部返回空白，放在报表上是减分项。

```dax
近30天用电 =
CALCULATE(
    [总用电量],
    DATESINPERIOD(dim_date[Date], MAX(dim_date[Date]), -30, DAY)
)
```

```dax
前30天用电 =
CALCULATE(
    [总用电量],
    DATESINPERIOD(dim_date[Date], MAX(dim_date[Date]) - 30, -30, DAY)
)
```

```dax
用电量环比 =
VAR v近30天 = [近30天用电]
VAR v前30天 = [前30天用电]
RETURN DIVIDE(v近30天 - v前30天, v前30天)
```
格式：`0.0%`，条件格式：正值红色（用电增加）、负值绿色。

> 用「近 30 天 vs 前 30 天」而不是「本月 vs 上月」，是因为数据窗口只有 90 天，
> 首尾月份是残缺月份（7 月从 2 号开始、9 月到 29 号结束），直接比月度总量会因为
> 天数不同而产生误导。滚动 30 天窗口两边天数恒等，对比才有意义。

### 报警

```dax
报警总数 = COUNTROWS(fact_alert)
```

```dax
活跃报警 = CALCULATE([报警总数], fact_alert[处理状态] = "活跃")
```

```dax
报警解决率 = DIVIDE([报警总数] - [活跃报警], [报警总数])
```
格式：`0.0%`

```dax
超功率报警数 = CALCULATE([报警总数], fact_alert[报警类型] = "超功率")
```

```dax
设备平均报警数 = DIVIDE([报警总数], [设备数])
```
格式：`0.0`

## 四、可复现

```bash
# 重建全部数据（天数与每类报警条数可调）
mysql -u root -p smart_home -e "CALL RebuildAll(90, 200);"
```

`RebuildAll` 会依次执行：明细生成 → 四张统计表回填 → 三类报警生成。
整条链路耗时约 3 秒，可反复执行。

调大天数（如 `RebuildAll(180, 400)`）后，记得同步修改 `dim_date` 的
`CALENDAR` 起止日期。

## 五、面试常见追问

**Q：为什么用存储过程造数，而不是 Python？**

造数逻辑要落在数据库侧才有意义 —— 这个项目的卖点是「用存储过程与触发器把统计聚合
自动化」，用 pandas 在库外生成再灌进去，等于绕开了要展示的能力。而且
`RebuildAll` 一条命令就能重建全量数据，任何人克隆仓库后都能复现。

**Q：为什么不用逐行循环？**

最初写成 `WHILE` 循环逐台设备逐条插入，5 万行要跑几分钟。改成
`INSERT ... SELECT` 交叉连接一次成型后，同样的数据量约 1 秒。MySQL 里逐行
DML 的开销主要在每个语句的事务与索引维护上，批量集合操作能摊薄掉这部分。

**Q：怎么保证模拟数据不是一堆随机数？**

用电量按「额定功率 × 负载率 × 系数」计算，并做上限截断，所以每条记录都能反算出
不超过额定功率，见第二节的校验表。同时设备关闭时段不写入记录，凌晨 1–5 点的照明和
风扇记录数为 0，小时曲线呈现真实的早晚高峰形态。

**Q：库里已经有四张统计表了，为什么 BI 里还要重算？**

见第一节末尾。简单说：统计表服务实时看板的固定粒度查询，BI 服务分析场景的任意维度
下钻，两者的查询模式不同，服务的是不同需求，不是重复劳动。
